## Implementation

- `Repository` is a `typing.Protocol` rather than an `abc.ABC` — structural typing means neither backend needs to inherit from anything, which matters because `SqliteAccountRepository` and `SqliteTransactionRepository` are necessarily per-entity-type classes (SQL needs entity-specific column names), not one generic class the way `InMemoryRepository[T]` can be.
- `InMemoryRepository` takes its backing dict as a constructor argument rather than creating one internally — this is what lets `InMemoryUnitOfWork` hand the *same* dict to a fresh repository instance on every `with` block, so writes from one transaction are visible to the next one, modeling a persistent store rather than a fresh, empty one each time.
- `UnitOfWork.__exit__` only calls `rollback()` when `self._committed` is still `False` — `commit()` is the only thing that sets it `True`. This means forgetting to call `commit()` and having an exception propagate through the block produce the exact same outcome (a rollback), which is the intended behavior: there's no special "error path" for rollback, it's just what not-having-committed means.
- `InMemoryUnitOfWork._begin` takes `copy.deepcopy` of both backing stores, not a shallow `dict(...)` copy. This distinction only matters because entities are mutated in place (`src.balance -= amount` mutates the `Account` object directly) — a shallow copy of the dict would produce a second dict pointing at the *same* `Account` objects, so "restoring" it would restore a dict of already-mutated objects, rolling back nothing. Confirmed this is load-bearing, not theoretical, via mutation testing (see Key Learnings).
- `SqliteUnitOfWork` requires its connection to be opened with `isolation_level=None` (done once, in `make_sqlite_connection`) — Python's `sqlite3` module's *default* behavior implicitly opens a transaction before any `INSERT`/`UPDATE`/`DELETE` and silently commits it under certain conditions (a notoriously confusing part of the stdlib). `isolation_level=None` disables all of that implicit behavior, making `BEGIN`/`commit()`/`rollback()` the only things that start or end a transaction — exactly the manual control a `UnitOfWork` needs to own.
- `DuplicateEntityError`/`EntityNotFoundError` are shared exception types raised by *both* backends' `add`/`update`, specifically so a caller coded against the abstract `Repository` interface doesn't also need to know which backend is underneath to catch the right exception. Without this, `InMemoryRepository.add` would naturally raise a plain `ValueError` while SQLite's `UNIQUE` constraint violation surfaces as `sqlite3.IntegrityError` — the abstraction would hold on the happy path and leak on the error path. `SqliteAccountRepository.add` explicitly catches `sqlite3.IntegrityError` and re-raises as `DuplicateEntityError`.
- `transfer_funds_unsafe` and `FailingRepository` exist purely to make the Unit of Work's value *measurable* rather than asserted — see Follow-up Questions and Key Learnings for what they actually showed.
- Not built: a real connection pool or `sessionmaker`-style per-request connection lifecycle (this exercise shares one SQLite connection across a whole test or demo run, which is a deliberate simplification documented here, not a production pattern), multi-entity-type genericism for the SQL repositories (each needs its own small, entity-specific class — a real ORM like SQLAlchemy exists mostly to remove exactly this boilerplate), and nested Units of Work (SQLite doesn't support nested transactions natively; this implementation assumes one `UnitOfWork` per `with` block, never two active at once on the same connection).

## Complexity

This exercise isn't about an algorithmic complexity trade-off — both backends are O(1) per repository operation (a dict lookup; an indexed SQL lookup by primary key) — so there's no naive-vs-fast benchmark table here. The property actually worth measuring is **behavioral equivalence across backends**, and **what atomicity actually buys**, both covered below.

## Follow-up Questions

**Why?**
The Repository + Unit of Work combination is the standard way to keep business logic (the funds-transfer rules) decoupled from persistence (SQL, an ORM, an in-memory test double) so the logic can be unit-tested fast and cheap, while still getting real transactional guarantees in production — and so swapping the persistence layer later doesn't require rewriting the rules that live on top of it.

**How exactly?**
A repository hides "how an entity gets stored and retrieved" behind `get`/`add`/`update`/`list`; a Unit of Work hides "how a group of writes becomes all-or-nothing" behind `commit`/`rollback`, and hands out repository instances that all participate in the *same* unit — in SQLite's case, literally the same open transaction; in the in-memory case, the same snapshot taken at the start.

**Which algorithm?**
Not an algorithm so much as an architectural pattern — Repository and Unit of Work are both named, well-established patterns (popularized in this exact pairing by Fowler's *Patterns of Enterprise Application Architecture*, and more recently by the "Cosmic Python" / *Architecture Patterns with Python* book, whose in-memory-snapshot-plus-real-database-transaction framing this implementation follows).

**Which library?**
Standard library only: `sqlite3` for the real backend, `copy.deepcopy` for in-memory rollback, `secrets` for generating ids, `typing.Protocol` for the repository interface (structural typing, no inheritance required).

**What happens internally?**
For SQLite, every statement issued between `BEGIN` and `COMMIT`/`ROLLBACK` is recorded in SQLite's own rollback journal (or WAL, depending on configuration) before being applied — `rollback()` is SQLite replaying that journal backwards, which is why it's exact regardless of how many statements or which tables were touched. For the in-memory version, there's no journal; `deepcopy` just pays the cost of the whole rollback guarantee up front, at `__enter__`, by duplicating every entity rather than tracking individual writes.

**How is it implemented?**
See [Implementation](#implementation).

**What if this fails?**
- **A failure in the second repository write, after the first repository was already mutated:** this is the actual point of the exercise (see Key Learnings) — the Unit of Work's rollback must undo both, not just prevent the failed one. Verified directly (`test_transfer_rolls_back_both_repositories_on_mid_transaction_failure`), parametrized across both backends.
- **The caller forgets to call `commit()`, with no exception at all:** still rolls back — verified directly (`test_exiting_the_with_block_without_calling_commit_rolls_back`), because the implementation treats "didn't commit" as the trigger, not "an exception happened."
- **A transfer of exactly the full balance:** must succeed, leaving the source at exactly 0 — the boundary this exercise's own `<` vs `<=` mutation (see Key Learnings) would get wrong in one direction. Verified (`test_transfer_boundary_at_exact_balance`).
- **Two backends disagreeing on anything, given the identical script:** checked directly, not assumed — `test_in_memory_and_sqlite_agree_on_an_identical_scripted_sequence` runs one hand-written sequence (two successful transfers, one failed one) against both and asserts the final sorted account and transaction lists are equal, with fixed `transaction_id`s and a fixed `clock` specifically so the comparison isn't defeated by incidental randomness (real ids and real timestamps would make even two *correct* backends' outputs look different).

**What trade-offs did you consider?**
- **Deep-copy snapshot/restore for in-memory rollback (chosen) vs. recording individual operations and replaying their inverses:** snapshotting is much simpler to get right (one `deepcopy` at the start, one restore on rollback, no need to define an "undo" for every operation type) at the cost of paying the copy cost for the *whole* store on every transaction, regardless of how small the actual change is — fine for a test double; a production in-memory store handling large datasets would need the operation-log approach instead.
- **One shared SQLite connection reused across many `UnitOfWork` instances (chosen, for this exercise) vs. a connection pool handing out a fresh connection per Unit of Work:** sharing one connection keeps the demo/test code simple and makes "does a later transaction see an earlier commit" trivially true, but doesn't reflect how a real multi-request service would manage connections (where pooling, and therefore one connection per request/Unit of Work, is the norm) — documented here as a scoped-down simplification, not advice for production use.
- **`Repository` as `Protocol` (chosen) vs. `ABC` with abstract methods:** `Protocol` means `SqliteAccountRepository` and `InMemoryRepository` don't need a common base class at all — they're interchangeable purely because they happen to implement the same four methods. An `ABC` would make the "this is the contract" intent more explicit at the cost of forcing every backend to inherit from it; for a Repository implementation per entity type per backend (already a lot of small classes), the looser coupling was worth it.
- **Revoking the whole transaction on any repository failure (chosen) vs. a "best effort, partial commit" mode:** a partial commit would mean deciding, per use case, which partial outcomes are "safe enough" to keep — that decision doesn't belong in generic Unit of Work infrastructure; it belongs (if ever) in domain logic that explicitly chooses to split a multi-step operation into separate, independently-committed Units of Work.

**How do you debug it?**
- For a "rollback didn't actually undo everything" bug, check whether the entities being mutated are the *same objects* still referenced by the backing store after rollback (`is` comparison, not `==`) — this is exactly how the shallow-vs-deep-copy snapshot bug (see Key Learnings) would show up: the restored dict looks right structurally but points at objects that were never actually reverted.
- For a "backends disagree" bug, `test_in_memory_and_sqlite_agree_on_an_identical_scripted_sequence` failing gives you the two divergent results side by side in the assertion diff — far faster to read than re-deriving which backend-specific test (if any) happened to catch it.
- For an "UPDATE affected the wrong row" class of bug in the SQL repositories, `cursor.rowcount` after the statement is the first thing to check — `0` means no row matched (should raise `EntityNotFoundError`), and an unexpectedly large number (more than 1, for a primary-key-filtered update) means the `WHERE` clause itself is broken, exactly the shape of mutation M5 below.

**How do you evaluate it?**
- **47 tests, 5/5 consecutive clean runs** — most tests run once per backend via the `backend` fixture's parametrization, plus a cross-backend differential test and 10 randomized-seed property tests.
- **Mutation check, 5 targeted mutations, each applied and reverted in isolation with `__pycache__`/`.pytest_cache` cleared before every run:**
  - `transfer_funds` skips `uow.accounts.update(dst)` (only the source account is explicitly updated): **caught only on `sqlite` — 0 failures on `in_memory`** (see Key Learnings: this is the central finding of the whole exercise, not an incidental result).
  - `UnitOfWork.__exit__` never calls `rollback()` at all: 18/47 failed, across both backends.
  - `InMemoryUnitOfWork`'s snapshot uses a shallow `dict(...)` copy instead of `copy.deepcopy`: 2/47 failed, both `in_memory`-only (structurally, this mutation cannot affect `sqlite` at all, since it only touches the in-memory snapshot code path).
  - `InsufficientFunds` check off-by-one (`<` → `<=`, rejecting an exact-balance transfer): 2/47 failed, both backends, exactly the boundary test designed to catch it.
  - `SqliteAccountRepository.update` drops its `WHERE id = ?` clause (updates every row instead of one): 14/47 failed, `sqlite`-only (structurally cannot affect `in_memory`, which has no SQL at all).

## Key Learnings

- **The central finding of this exercise: a bug invisible on one backend was caught only because the identical test suite also ran against a second, structurally different one.** Skipping `uow.accounts.update(dst)` in `transfer_funds` passed every single `in_memory` test — because `InMemoryRepository` stores entities by reference, and `dst.balance += amount` had already mutated the shared object in place; the dict's own copy of that reference was already "updated" with no call to `.update()` ever required. The identical mutation failed 13 `sqlite` tests immediately, because SQL has no equivalent of "mutate the object in place and the database automatically notices" — nothing updates a row except an explicit `UPDATE` statement reaching the database. Neither backend's test suite alone would have caught this reliably forever; running the same suite against both is what makes a bug like this visible instead of silently backend-dependent. This is also precisely the real-world risk the whole exercise is about: code that happens to work against an in-memory fake, developed and tested only against it, can hide a bug that a real database would expose immediately.
- **Two mutations landed as exact backend-exclusive mirror images of each other, which is the expected and correct result, not a coincidence to investigate further.** The shallow-copy-snapshot mutation can only ever affect `InMemoryUnitOfWork` (it touches code SQLite's path never executes), and the dropped-`WHERE`-clause mutation can only ever affect the SQL repositories (there's no equivalent "update every row" failure mode possible for a dict). Seeing a mutation fail exclusively on one backend is itself informative — it confirms the mutation targeted backend-specific code, as intended, rather than being a sign the cross-backend test parametrization isn't actually exercising both paths.
