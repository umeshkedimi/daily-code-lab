## Implementation

- `_b64url_decode` translates `-`/`_` to `+`/`/` itself and calls `base64.b64decode(..., validate=True)` rather than `base64.urlsafe_b64decode`, which internally calls plain `b64decode` **without** `validate=True` — meaning it silently *discards* any character outside the base64 alphabet instead of raising. This was a real bug caught by this exercise's own tests, not assumed correct going in (see Key Learnings).
- `JWT.decode` computes the expected signature **before** ever parsing the payload as JSON, and raises on a mismatch before attempting `json.loads`. This ordering matters: a tampered payload that happens to still be syntactically valid JSON must still be rejected as a *signature* failure, not accidentally accepted because decoding never got far enough to notice.
- `JWT.decode` never reads the header's `alg` field — it always computes HMAC-SHA256 over the raw segments and compares via `hmac.compare_digest`. This is what makes the "alg: none" attack (forging a token with an empty signature and a header claiming no algorithm) fail the same way any other wrong signature fails, rather than needing an explicit "reject alg=none" special case that could be forgotten for some other `alg` value.
- `AuthService` claims per access token: `sub`, `type: "access"`, `iat`, `exp`, and a `jti` nonce (`secrets.token_hex(8)`) — the nonce exists specifically so two tokens issued at the same clock reading aren't byte-identical, which matters for audit trails and is a prerequisite for ever adding access-token-level revocation later (not built here, since access tokens are intentionally stateless).
- Refresh tokens are `secrets.token_urlsafe(32)` random strings, never JWTs; only `sha256(raw).hexdigest()` is stored in `_refresh_store`, keyed by that hash. `refresh()` looks up by hash, never compares raw strings directly.
- `_RefreshRecord` tracks `used` and `revoked` as **separate** booleans, deliberately not collapsed into one "is this token dead" flag, because they're checked in a specific order for a reason: `revoked` is checked first in `refresh()`, so once a family is shut down, every token in it (including ones never individually used) uniformly raises `RevokedRefreshToken` — `used` is checked second, so a token being reused for the first time still gets the more specific `ReplayDetected` (which also triggers the revocation) rather than being swallowed by a generic "revoked" message before that distinction is ever made.
- `_revoke_family` is a linear scan over the whole `_refresh_store` — fine for this exercise's scale; a production version with many users would index records by `family_id` (a `Dict[str, List[_RefreshRecord]]`) to make revocation O(family size) instead of O(all refresh tokens ever issued, across all users).
- Not built: refresh-token expiry *sliding* on each rotation (this implementation keeps the original `expires_at` fixed at first login, so a very long-lived session still needs eventual re-login — a deliberate choice, not an oversight, since "rotation extends the session forever" and "rotation just proves continued possession of a valid token" are different security postures), multi-device/concurrent-session handling beyond independent families, and any actual network transport (this is the auth logic only, not an HTTP layer).

## Complexity

- `JWT.encode`/`JWT.decode`: O(claims size) — one HMAC computation and one or two base64/JSON (de)serializations, no scaling concern.
- `AuthService.login`/`refresh`: O(1) amortized — one dict insert/lookup by hash.
- `AuthService._revoke_family`: O(N) in the total number of refresh-token records ever stored (across all users, all time, in this in-memory implementation) — the one place in this design that doesn't scale past a toy/demo size; see Implementation for the indexing fix.
- No empirical timing/throughput measurement for this problem — the properties that matter here are correctness-under-adversarial-input (tampering, replay, revocation propagation) rather than a complexity trade-off with a naive alternative to benchmark against, which is why this write-up leans on the mutation/fuzz results below instead of a performance table.

## Follow-up Questions

**Why?**
Short-lived stateless access tokens plus rotating, revocable refresh tokens is the standard shape of modern session management (OAuth2 refresh token rotation, most "remember me" implementations) precisely because it balances two needs that pull in opposite directions: access tokens need to be cheap to verify on every request (no DB hit), but *some* mechanism needs to be revocable when a session is compromised — refresh tokens, checked rarely, are where that server-side control lives.

**How exactly?**
An access token is self-contained proof ("the holder of the secret says this subject is valid until this time") checked by recomputing a signature; a refresh token is a reference ("look this up and see what state it's in") checked against mutable server-side records — rotation and replay detection are only possible on the reference side, because only it can remember "this specific one was already used."

**Which algorithm?**
HS256 (HMAC-SHA256) for the JWT signature — a symmetric scheme (one shared secret verifies and signs), appropriate for a single-service auth system; an asymmetric scheme (RS256/ES256) would matter once other services need to *verify* tokens without being trusted to *issue* them. Refresh-token rotation with family-wide revocation on reuse is the standard pattern described in the OAuth 2.0 Security Best Current Practice (RFC area; not itself a named "algorithm" so much as a protocol convention).

**Which library?**
Standard library only: `hmac` (HMAC construction and constant-time comparison), `hashlib` (SHA-256), `base64` (segment encoding), `json` (claims serialization), `secrets` (cryptographically secure random tokens and nonces — never Python's default `random`, which is not safe for anything security-sensitive).

**What happens internally?**
`hmac.new(secret.encode(), signing_input, hashlib.sha256).digest()` runs HMAC's nested-hash construction (`H((K XOR opad) || H((K XOR ipad) || message))`), which is specifically designed so that knowing the hash of some message under a key reveals nothing useful about the key or about the hash of a different message — this is why a signature can safely travel in a token that an untrusted client holds and later presents back.

**How is it implemented?**
See [Implementation](#implementation).

**What if this fails?**
- **A single bit flipped anywhere in the signature or payload:** must always be caught as `InvalidSignature` — verified with 40 randomized bit-flip trials (20 against the signature, 20 against the payload), each targeting a deterministically-guaranteed-different byte (a raw bit flip before re-encoding, not a text-level character substitution, which avoids any chance of the flip coincidentally decoding to the same bytes).
- **A forged `alg: none` token:** rejected the same way as any other bad signature, because `decode()` never consults the header to decide how to verify — verified directly (`test_alg_none_downgrade_is_rejected`).
- **A client retries a refresh request after losing the response** (e.g. network timeout, but the server's rotation already happened): this looks identical, from the server's point of view, to an attacker replaying a stolen stale token — both present an already-`used` refresh token. This implementation cannot distinguish the two cases and deliberately doesn't try to; it always revokes the family. The cost is a legitimate user occasionally getting logged out by their own network hiccup; the alternative (assume reuse is probably innocent) is the wrong default for an auth system. Documented here rather than "fixed," because there is no fix that doesn't require information this server doesn't have (e.g. the client proving *which* response it lost).
- **Replaying a token from several rotations back**, not just the immediately-previous one: still caught, because every record (not just the most recent) is retained and checked by hash lookup, and `used`/`revoked` state persists on it indefinitely — verified (`test_replay_can_be_detected_even_several_rotations_back`) with a 5-deep rotation chain.

**What trade-offs did you consider?**
- **Revoking the whole family on any replay (chosen) vs. only rejecting the specific reused token:** rejecting just the reused token and leaving the rest of the chain alone is friendlier to the "client retried" false-positive case, but means a genuine theft just gets the stolen token's specific use blocked — the attacker's own freshly-rotated token (if they got further than one step) would keep working. Revoking the family trades a worse false-positive experience for actually containing a real compromise, which is the right default for session security.
- **Fixed `expires_at` set once at login (chosen) vs. sliding expiry extended on every rotation:** a sliding window means a continuously-active session never truly ends, which is a bigger blast-radius window if a refresh token is silently exfiltrated and used just often enough to keep extending itself. A fixed ceiling forces periodic full re-authentication regardless of activity.
- **Hashing refresh tokens at rest (chosen) vs. storing them raw for simpler lookup:** hashing means a leaked `_refresh_store` (e.g. a DB dump) doesn't hand out directly-usable tokens, at the cost of needing to hash the presented token on every lookup — a cheap SHA-256 call, not a real cost.
- **`hmac.compare_digest` (chosen) vs. a plain `==` comparison:** both are functionally identical for every test in this suite (see Key Learnings) — the difference is purely about timing side-channels, which functional tests cannot observe, and is a case where "the tests all still pass" is not evidence the mutation is safe to ship.

**How do you debug it?**
- For a tampering-not-detected bug, print `(expected_sig.hex(), actual_sig.hex())` right before the comparison — a one-bit difference on a 32-byte digest is immediately visible, and if they're equal when they shouldn't be, the bug is almost certainly upstream (the wrong bytes going into `signing_input`, e.g. using the *new* payload to compute the signature instead of the one actually being verified).
- For a replay-detection bug, `_refresh_store[hash].used` and `.revoked`, read directly, distinguish three different failure shapes: never set (the rotation step itself is broken), set but the family-revocation loop didn't run (check `_revoke_family`'s `family_id` filter), or set correctly but `refresh()`'s check order is wrong (reversing the `revoked`-before-`used` check order changes which exception type a *third* presentation of an already-replayed token raises — not a functional bug per se, but a behavior worth being deliberate about, not accidental).
- The randomized invariant test (`test_random_sequences_of_operations_never_violate_family_revocation`) is the actual tool of record for this kind of stateful bug: a hand-picked scenario only proves the specific sequence you thought to write down is handled; the random one proves a *global* property (once compromised, always rejected) holds under sequences nobody specifically designed.

**How do you evaluate it?**
- **80 tests, 5/5 consecutive clean runs** (fixed `pytest.mark.parametrize` seeds for the bit-flip fuzzing and the randomized operation-sequence test — reruns confirm environment stability, not randomness per se).
- **Mutation check, 6 targeted mutations, each applied and reverted in isolation with `__pycache__`/`.pytest_cache` cleared before every run:**
  - `hmac.compare_digest` → `==`: **0/80 failed — expected, and not a coverage gap** (see Key Learnings: this is checked by code inspection, not a functional test, on principle).
  - `decode()`'s expiry check removed entirely: 2/80 failed.
  - `refresh()` forgets to set `record.used = True`: 4/80 failed.
  - `refresh()` skips the `revoked` check: 18/80 failed (mostly in the randomized invariant test, which is exactly the kind of violation it exists to catch).
  - `_revoke_family()` made a no-op: 18/80 failed (same signature as the previous mutation — both ultimately mean "a revoked family doesn't actually block anything," reached two different ways).
  - `decode()`'s segment-count guard removed (lets a malformed token crash on tuple-unpacking instead of raising `MalformedToken`): 4/80 failed.

## Key Learnings

- **`validate=True` on base64 decoding is not a default, and the unvalidated default is a real vulnerability class, not a style nitpick.** `base64.urlsafe_b64decode` (and plain `b64decode` without the flag) silently discards any out-of-alphabet character instead of raising — so a corrupted or adversarially-crafted token segment decodes to *some* bytes rather than failing cleanly. This was caught directly by `test_decode_rejects_non_base64_signature_segment` failing on the first test run, not assumed safe going in: a bad-looking test failure ("why didn't this raise MalformedToken?") traced straight back to this default. Lesson: any time a format's decoder has a lenient/strict mode, assume the lenient one is the default and verify which one you're calling, rather than trusting a function name like `urlsafe_b64decode` to imply strictness.
- **Two genuinely different kinds of "zero test failures" on a mutation, and telling them apart matters.** 2026-10-08's rate-limiter problem found a mutation that passed every test and turned out to be a *real coverage gap* (fixable by adding a test that asserts the missing lower bound). This problem's `compare_digest` → `==` mutation also passes every test, but for a structurally different reason: no functional test *can* distinguish them, because both produce byte-for-byte identical accept/reject decisions on every input — the only difference is how long the comparison takes to run depending on how many leading bytes happen to match, which is an information leak about the comparison's intermediate state, not about its output. The fix for the rate limiter was "write a test that checks the missing property." There is no equivalent fix here within a functional test suite — the guarantee has to come from reading the code and confirming `hmac.compare_digest` (not `==`) is used, which is exactly why the comment in `JWT.decode` calls this out explicitly for a future reader, and why this write-up records it as checked-by-inspection rather than claiming test coverage it doesn't have.
