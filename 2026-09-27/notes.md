## Implementation

- `DisjointSet` stores `parent`/`rank`/`size` dicts (works over arbitrary hashable elements, not just `0..n-1`), plus `find_hops`, a cumulative counter of pointer-following steps incremented inside `find()` — the instrument every measurement in this exercise reads from.
- `find(x)` walks parent pointers to the root, counting hops, then — if `path_compression` is on — makes a second pass repointing every visited node directly at the root ("full compression", not path halving/splitting).
- `union(x, y)`: with `union_by_rank` off, the fixed, asymmetric convention is `parent[find(y)] = find(x)` (`y`'s root always attaches under `x`'s root) — deliberately asymmetric, since a symmetric rule has no adversarial order to exploit. With it on, the lower-rank root always attaches under the higher-rank one, and rank increments only when the two ranks tie.
- `depth(x)` / `max_depth()` read the current tree shape without mutating it — a structural check independent of `find_hops`'s work-counter.
- `chain_union_order(n)` and `doubling_union_order(n)` are two different adversarial constructions (see Follow-up Questions for why two, not one); `random_union_order(n)` is the non-adversarial control.
- `NaiveGroups` is an O(n)-per-op reference model (a plain list of sets) used only for differential testing — correctness by triviality, not by being fast.
- `kruskal_mst` sorts edges once and uses `union()`'s own return value as the cycle check — no separate cycle-detection logic exists to fall out of sync with it. Stops early once `n - 1` tree edges are chosen (never even sorts through the rest on a sparse-enough graph in practice, though the sort itself is still O(E log E) up front). Returns a minimum spanning *forest* plus a component count on disconnected input, rather than raising.
- `prim_mst_weight` (O(V²), independent of `DisjointSet` entirely) and `mst_forest_weight_via_prim` (runs it once per component, itself found via a `DisjointSet` — a legitimate use, since finding components isn't the thing being cross-checked) serve as the efficient oracle for larger graphs; `brute_force_mst_weight` (exhaustive over all `(n-1)`-subsets) is the maximally-trustworthy oracle for tiny ones.
- Not built: path splitting/halving (compression variants that don't need a second full pass — a real optimization, not attempted here since full compression already demonstrates the claim); union by size instead of rank (an equally valid, commonly-used alternative with the same asymptotic guarantee); a `split`/undo operation (DSU fundamentally can't support one efficiently — merges are one-directional by design).

## Complexity

- `find`/`union`/`connected` with both optimizations: amortized O(α(n)) — for any n representable in this universe, α(n) ≤ 4, i.e., effectively O(1). With only one, or neither, see the measured results below — the honest complexity is conditional on which optimizations are actually enabled, which is the entire point of building this with both as switches.
- `kruskal_mst`: O(E log E) for the sort, O(E · α(V)) for the union-find work — dominated by the sort.
- `prim_mst_weight`: O(V²) — the simple array-scan version, not the O(E log V) binary-heap version, since it exists purely as an independent-by-construction oracle, not as a competitor implementation.
- `brute_force_mst_weight`: O(C(E, n-1) · n · α(n)) — deliberately exponential, usable only for tiny graphs.

## Follow-up Questions

**Why?**
Any structure that only ever *merges* groups and needs to answer "are these two in the same group?" cheaply — network connectivity, image-segmentation region merging, detecting cycles while building a spanning tree — reduces to this exact problem. It's a small enough structure to implement fully in an interview, and it's one of the few places in a CS curriculum where the amortized-complexity argument (Tarjan's inverse-Ackermann bound) is both famous and genuinely checkable by hand on paper — which made it worth actually measuring rather than reciting.

**How exactly?**
`find(x)` walks parent pointers to the root, optionally flattening the path behind it. `union(x, y)` finds both roots and, if different, attaches one under the other — by a fixed rule if `union_by_rank` is off, by rank if it's on — and reports whether a merge happened. Kruskal's algorithm sorts all edges by weight and greedily takes each one that `union()` reports as a genuine merge (i.e., doesn't close a cycle), stopping once a spanning tree (or forest) is complete.

**Which algorithm?**
Union-Find with path compression and union by rank (the standard combination proven to give the inverse-Ackermann amortized bound), and Kruskal's algorithm (a greedy algorithm correct by the cut property: the cheapest edge crossing any cut belongs to *some* MST, and processing edges in increasing weight order while skipping cycle-closing ones is exactly exploiting that property one edge at a time).

**Which library?**
Standard library only (`math`, `random`, `itertools.combinations` for the brute-force oracle). No graph library — the whole exercise is about not treating either DSU or Kruskal as a black box.

**What happens internally?**
Each `find()` call is a linked-list-style pointer chase through the `parent` dict; compression is a second such chase that mutates every visited entry. There's no tree object, no node class — "the tree" is entirely implicit in the `parent` dict's structure, which is why `depth()`/`max_depth()` (reading that structure) and `find_hops` (counting the work `find()` actually does) are two genuinely different, independently useful measurements of it.

**How is it implemented?**
See [Implementation](#implementation).

**What if this fails?**
- **No optimizations, adversarial order:** `chain_union_order(n)` forces `depth(0) == n - 1` exactly, at every tested size (10 through 10,000) — not "large," the precise worst case.
- **Rank only, the same adversarial order:** stays at `max_depth == 1` — union-by-rank doesn't just survive this particular attack, it defeats it almost completely, because the order happens to always offer rank a correct shallow placement.
- **Rank only, a *different* adversarial order** (`doubling_union_order`, pairing only equal-rank trees — the one case where rank's tie-break logic never actually fires): `max_depth` lands exactly on `floor(log2 n)` at every power of two tested (128 through 65,536) — confirming the textbook bound is tight, not merely an upper bound nobody reaches.
- **Compression only, a fixed small query budget** (500–20,000 queries) **against a huge chain:** average cost per query grows with n (1.00 → 1.05 → 1.41 → 4.28 hops/query as n goes 128 → 65,536) — most of a 65,536-element chain is still uncompressed after only 20,000 queries.
- **Compression only, a query budget that scales with n** (5n queries on the same chains): average cost stays essentially flat (1.19–1.20 hops/query) — the same optimization, the same pathological input, a completely different-looking outcome depending purely on how much work is given a chance to amortize over.
- **A non-adversarial (random) union order, no optimizations at all:** stays well-behaved (`max_depth < 10·log2(n)` at n=5,000) — the pathology needs a *specific* order to appear; the real-world risk is an adversary who can choose that order, not naive Union-Find being unconditionally bad.
- **Kruskal on a disconnected graph:** returns a valid minimum spanning forest and the correct component count, rather than raising or silently returning a wrong/partial tree — verified directly, including the exact edge count (`n − components`, not `n − 1`).

**What trade-offs did you consider?**
- **Full path compression (chosen) vs. path halving/splitting:** full compression does two full passes per `find()` (walk up, then flatten); halving/splitting achieve the same amortized bound in one pass by repointing every node to its *grandparent* during the initial walk. Full compression was chosen for this exercise because its effect (every visited node now points directly at the root) is the simplest to state and test exactly (`d.depth(0) <= 1` after one `find()`); the asymptotic guarantee is identical either way.
- **Union by rank (chosen) vs. union by size:** both give the same O(log n) worst-case depth bound and the same amortized result combined with compression; rank was chosen because the depth bound it produces (`floor(log2 n)`) is the one most directly and exactly testable by construction, whereas size's exact worst-case depth bound is a slightly less clean statement.
- **Two different adversarial orders (chosen) vs. one "the" adversarial order:** there is no single order that's simultaneously the worst case for "no rank" *and* tight for "rank enabled" — the chain order is a strong attack on the former and a near-best-case for the latter; the doubling order is precisely the case where rank's mechanism can't help at all (equal ranks, no tie-break to make), which is what makes it the order that reaches the bound tightly. Reporting one order and claiming it demonstrates both properties would have been quietly wrong.
- **Fixed vs. scaled query budget when measuring compression's benefit:** reporting only the scaled-budget number (small, flat) would make compression alone look as good as the combination — true only if the caller happens to run enough queries; reporting only the fixed-budget number (growing) would make it look like compression barely helps. Both are shown side by side specifically so this isn't a choice made by omission.
- **Sorting all edges up front in Kruskal (chosen) vs. a lazily-popped min-heap:** sorting is simpler and asymptotically identical (both O(E log E)); a heap would only win if the algorithm frequently stopped very early relative to E, which isn't the common case this implementation targets.

**How do you debug it?**
- `depth(x)`/`max_depth()` are the read-only instruments for "what does the tree actually look like right now" — used throughout to separate *structural* claims (how deep is it) from *work* claims (how many hops did operations actually cost), which is exactly the distinction that would be easy to blur into one number and get subtly wrong conclusions from.
- `find_hops`, read as a **delta** (snapshot before, snapshot after) rather than as a running total, is how per-phase cost is measured. Forgetting the snapshot — using the raw cumulative value directly — was an actual bug caught while building this exercise's own test suite (below), not a hypothetical one.
- For Kruskal, comparing against two independently-built oracles (brute force, then Prim) rather than one means a bug shared between Kruskal and a single oracle can't hide; the oracles were cross-checked against each other first for the same reason.

**How do you evaluate it?**
- 74 tests, 15/15 consecutive clean runs, plus a mutation check: 10 deliberate breaks (the exact compression bug below, a skipped rank-tie increment, a wrong swap comparison, hop-counting placement, unsorted Kruskal edges, an inverted cycle check, an off-by-one stopping condition, `component_size` reading the wrong node, a broken doubling schedule, and a naive-reference bug) — **all 10 caught**.
- Differential testing: `DisjointSet` (all four optimization combinations) against `NaiveGroups` over randomized operation sequences, 10 seeds each.
- Exact-equality assertions wherever an exact answer exists, not just "roughly right": `depth(0) == n - 1` for the chain worst case; `max_depth == floor(log2 n)` for the tight rank bound; `find_hops` deltas of exactly `n - 1` for a single cold `find()` and `<= 1` for the one immediately after.
- Kruskal cross-checked against brute force (tiny graphs), against Prim (larger graphs, 150–200 random trials including disconnected ones, 0 mismatches both times it was run), and against basic spanning-tree/forest validity (no cycles, correct edge count) directly on the chosen edges.
- Not evaluated: DSU under concurrent access (this implementation has no locking and none was claimed); graphs large enough that Kruskal's O(E log E) sort becomes the practical bottleneck; negative-weight edges (Kruskal handles them correctly since it only requires a total order on weights, but this wasn't specifically exercised).

## Key Learnings

- **A real bug, found by a test that checked an exact number instead of "did it get faster":** the path-compression loop used `node, self._parent[node] = self._parent[node], root` — a swap-idiom one-liner that looks correct and is not. Python evaluates tuple-target assignments left to right, so by the time the second target `self._parent[node]` is evaluated, `node` has *already* been reassigned to the next node in the walk by the first target — so the assignment silently repoints the wrong dictionary entry (usually one that's already correct) while leaving the intended one untouched. Confirmed directly: `node, p[node] = p[node], root` on `p = {0: 1, 1: 2, 2: 2}` leaves `p[0]` completely untouched. A test asserting "the path is faster afterward" would likely have passed anyway (partial, accidental compression from repeated calls still trends downward); the test that caught it asserted the *exact* depth (`<= 1`) immediately after exactly one `find()` call. The general lesson: Python's swap idiom (`a, b = b, a`) is safe for independent names; it is not safe the moment one target is a subscript/attribute whose *own* index depends on another target in the same assignment.
- **My own first "amortized" test was measuring the wrong quantity, for a reason worth naming precisely:** `find_hops` is a cumulative counter since object creation, and building an adversarial structure via `union()` itself calls `find()` internally — so a test that read `d.find_hops` directly after a small query loop, without snapshotting a baseline first, was silently including 19,997 hops of *construction* cost in what was meant to measure 500 queries' worth of work. The fix (snapshot before, subtract after) is the same pattern already used correctly elsewhere in the same file — the inconsistency itself, not just the bug, is the lesson: a measurement pattern used correctly once still has to be applied deliberately every time it's reused, not assumed.
- **The "same" worst-case idea needs a different adversarial input depending on exactly what's being claimed.** Reusing one adversarial order for both "no-rank blows up" and "rank's bound is tight" would have quietly proven only the first — the chain order happens to be nearly ideal for union-by-rank, not adversarial to it. This is the general shape of a mistake worth watching for beyond this one exercise: an input engineered to break configuration A is not automatically an input that stresses configuration B, even when both are "the same kind of worst case" in casual description.
