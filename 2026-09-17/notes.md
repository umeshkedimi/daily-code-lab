## Implementation

- `UnifiedResponse` is the one shape every adapter must produce regardless of provider: `content`, `model`, `provider`, `prompt_tokens`, `completion_tokens`, `latency_ms` — a caller of `LLMGateway.complete()` never sees an OpenAI-shaped or Anthropic-shaped object, only this one.
- `OpenAIAdapter.complete()` sends the unified `messages` list essentially as-is (OpenAI's own format already matches the unified shape) and parses `choices[0].message.content` and `usage.prompt_tokens`/`usage.completion_tokens` directly.
- `AnthropicAdapter.complete()` does real translation work: it filters `messages` for `role == "system"` entries, joins their content into Anthropic's separate top-level `system` field, and passes the *remaining* messages as Anthropic's `messages` array; it always includes `max_tokens` (Anthropic rejects a request without it — this isn't optional the way it effectively is for OpenAI); it reads Anthropic's response `content` as a list of typed blocks and concatenates only the `"text"` blocks; and it maps Anthropic's `usage.input_tokens`/`usage.output_tokens` onto the unified `prompt_tokens`/`completion_tokens` fields.
- `retry_async`/`RetryPolicy`/`is_retryable_http_error` are a self-contained copy of the pattern from the standalone retry exercise (kept local to this day's folder rather than importing across day-folders, consistent with each day being independently runnable), with one deliberate change: `is_retryable_http_error` here also treats HTTP `429` as retryable, not just `>=500` — a realistic refinement, since rate-limiting is exactly the kind of transient condition retry-with-backoff exists for, and the original exercise's notes explicitly called this out as a reasonable classifier swap.
- `LLMGateway.complete()`'s candidate loop is the core of the exercise: for `(model, *fallback_models)`, resolve the adapter, call it through `retry_async`, and on **any** failure — `UnknownProviderError` from resolution, `RetryError` from exhausted retries, or a bare `except Exception` for literally anything else — record a string describing what happened in `attempts[candidate]` and move to the next candidate. Only when every candidate has been tried and failed does `AllModelsFailedError(attempts)` raise, carrying the full per-candidate detail.
- The bare `except Exception` in that loop is intentional, not a catch-all sloppiness: this function's entire job is "isolate one candidate's failure so it can't block the rest of the chain," and an exception type nobody anticipated is still exactly the kind of failure that should be isolated, not allowed to crash the whole request. This was validated empirically, not just argued for — see the real finding below.
- The FastAPI layer (`/v1/chat/completions`) is intentionally thin: Pydantic request/response models, one call into `gateway.complete()`, and one `except AllModelsFailedError` mapped to a `502` carrying the full `attempts` dict as the error detail — a caller of this endpoint gets the same "why did every option fail" detail a direct caller of `LLMGateway` would get, not a generic message.
- Edge case handled: a candidate string with no `/` (e.g. just `"gpt-4o-mini"`) or an unrecognized provider prefix is caught by `_resolve()` and recorded as a normal attempt failure — it doesn't raise out of `complete()` early or skip the remaining fallback candidates.
- Not handled (explicitly out of scope): streaming responses (this gateway assumes one complete response per call, not token-by-token, same limitation named in the tool-calling agent exercise); cost tracking/budget enforcement across models (a real LiteLLM deployment tracks $ spent per model/key); and load-balancing across multiple keys/deployments of the *same* model (this gateway picks the first working candidate in a fixed priority order, not the least-loaded or cheapest one).

## Complexity

- Time: O(candidates × max_attempts) provider calls in the worst case (every candidate exhausts its full retry budget before the next is tried); O(1) in the common case (the primary candidate succeeds on its first attempt).
- Space: O(candidates) for the `attempts` dict — bounded by how many fallback models were configured, not by anything unbounded.

## Follow-up Questions

**Why?**
Any codebase calling more than one LLM provider (or even one provider across multiple models with different reliability/cost trade-offs) either duplicates provider-specific request/response handling at every call site, or centralizes it once behind a unified interface — which is exactly the problem LiteLLM (and internal "model gateway" services at most companies doing this at scale) exists to solve. Building a minimal version of it directly is what makes reading LiteLLM's own source, or debugging a production gateway service, legible instead of a black box.

**How exactly?**
A caller sends one request shape (`model: "provider/model_name"`, unified `messages`, optional `fallback_models`) to `LLMGateway.complete()` or the `/v1/chat/completions` endpoint. The gateway resolves `model` to a registered adapter, calls it through the retry wrapper, and — on any failure — moves to the next model in `fallback_models`, repeating until one succeeds or the list is exhausted.

**Which algorithm?**
Not a classical algorithm — this is provider abstraction (the Adapter pattern, one implementation per real backend behind one interface) composed with the same retry-with-backoff technique from an earlier exercise, plus a simple ordered-fallback-chain for cross-model resilience. The interesting design decision isn't an algorithm, it's the boundary between what retry handles (same candidate, transient failure) and what fallback handles (different candidate, any other failure).

**Which library?**
`httpx` for real async HTTP in both adapters (and, critically, `httpx.MockTransport` for testing — a first-class part of the library, not a bolted-on test double); `fastapi`/`pydantic` for the thin HTTP layer, consistent with the earlier FastAPI/LangChain gateway exercise. No LLM-provider SDKs (`openai`, `anthropic`) — the adapters speak each provider's raw HTTP API directly, which is what actually demonstrates understanding the wire format rather than delegating that understanding to a client library.

**What happens internally?**
`httpx.AsyncClient.post()` serializes the Python dict passed as `json=` into a request body and sets `Content-Type: application/json`; on the way back, `.json()` deserializes the response body. `httpx.MockTransport` intercepts at the transport layer (below the client's request-building logic but above any real socket), so the JSON encoding of the outgoing request and decoding of the incoming response both genuinely execute in tests — only the actual network I/O is replaced. This is a meaningfully higher-fidelity test than monkeypatching `adapter.complete` itself, because a bug in how the request body is built would still be caught.

**How is it implemented?**
See [Implementation](#implementation) above.

**What if this fails?**
- A single transient failure on the primary model (one 500, one timeout): retried within budget, succeeds, no fallback needed — verified directly (a mock transport that fails once then succeeds needed exactly 2 calls, confirming retry did its job before fallback was even considered).
- The primary model/provider is persistently down: retries exhaust, `RetryError` is caught by the gateway loop, and the next fallback candidate is tried — verified with a primary that always 500s and a fallback (a *different provider*) that succeeds.
- A non-retryable error (400 bad request) on the primary: fails after exactly one call, not the full retry budget, before moving to fallback — verified by asserting the mock transport was hit exactly once, not three times.
- Every configured candidate fails: `AllModelsFailedError` carries a dict of every candidate's specific failure reason — verified both at the `LLMGateway` level and through the FastAPI endpoint (502 response body includes the same per-model `attempts` detail).
- **A real, unanticipated failure mode surfaced during live smoke testing** (not simulated): with an empty `OPENAI_API_KEY`, the OpenAI adapter's `Authorization: Bearer ` header (trailing space, empty token) is rejected *client-side* by httpx itself as `LocalProtocolError: Illegal header value` — this never reaches the network at all. Meanwhile the empty Anthropic `x-api-key: ""` header is syntactically valid, so that request *does* reach the real server and comes back as a genuine `401 Unauthorized`. Two completely different failure shapes (`httpx.LocalProtocolError` — not a subclass of any `httpx.HTTPError` — vs. a real `httpx.HTTPStatusError`), neither specifically coded for, and the gateway's `except Exception` boundary handled both correctly anyway, recording each in `attempts` and (in the two-candidate case) still failing cleanly with full detail rather than crashing. This is the concrete justification for the "deliberately broad exception handling at this one boundary" design choice, not a hypothetical one.

**What trade-offs did you consider?**
- Real HTTP calls to each provider's raw API (chosen) vs. using each provider's official SDK: hand-rolling the HTTP layer is more code and more provider-specific knowledge to get right, but it's what actually demonstrates (and tests, via `MockTransport`) the wire-format translation this exercise is about — using `openai`/`anthropic` SDKs would have hidden exactly the part being practiced.
- `except Exception` as the isolation boundary in the fallback loop (chosen, and empirically justified above) vs. a curated list of expected exception types: a curated list reads as more precise, but the live smoke test's `LocalProtocolError` is direct evidence that "expected" exception lists miss real failure modes in practice — for this one specific boundary (isolate a candidate, try the next), broad handling is the more correct choice, not a shortcut.
- Ordered fallback list (chosen) vs. a smarter router (e.g. cheapest available, least latency historically, load-balanced across multiple keys of the same model): an ordered list is simple and fully explains its own behavior by inspection; a smarter router is what a real production gateway would eventually want, and is explicitly named as out of scope rather than attempted partially.
- Self-contained retry logic copied into this day's file (chosen) vs. importing it from the earlier retry exercise's folder: day-folders in this repo aren't set up as an importable package (they're dated directories, not a Python package with `__init__.py`/path wiring), so treating each day as self-contained avoids a fragile cross-folder import for a small enough amount of code to justify duplicating — the conceptual reuse is real even though the code isn't literally shared.

**How do you debug it?**
- `AllModelsFailedError.attempts` (and the FastAPI endpoint's `502` body) is the primary debugging surface — it's a dict from candidate string to a specific failure reason, so "why did my request fail" never requires reproducing the issue with a debugger; the answer is already in the exception.
- To debug the wire-format translation specifically, `test_anthropic_adapter_separates_system_message_and_sets_max_tokens` captures the *actual outgoing request body* via the mock transport and asserts on it directly — the technique to reach for whenever "is the request I think I'm building the request that's actually being sent" is in doubt.
- To reproduce retry-vs-fallback boundary behavior deterministically, a mock transport with a closure-captured call counter (`calls["n"] += 1`) is the pattern used throughout the test suite — it turns "how many times was this actually called" into a directly assertable fact instead of an inference from timing.
- For the real, live failure mode found during smoke testing, the fix for future debugging is now written down here rather than needing to be rediscovered: an empty/missing API key produces two *different* exception shapes depending on provider, and neither looks like a typical "auth failed" error at a glance (`LocalProtocolError` in particular reads more like a bug than a credentials problem on first encounter).

**How do you evaluate it?**
- Wire-format fidelity: both adapters' request-building and response-parsing verified against fixtures shaped exactly like each provider's real documented API, including the Anthropic-specific system-message extraction and required `max_tokens`, confirmed by inspecting the literal JSON sent over the mock transport.
- Routing: provider-prefix dispatch verified for both configured providers; an unconfigured/malformed model string verified to fail as a normal, informative attempt rather than crashing the whole request.
- Retry vs. fallback boundary: verified as three distinct, separately-tested behaviors — recovers via retry alone (2 calls, no fallback triggered), exhausts retry then falls back (a different provider serves the request), and fails fast on a non-retryable error without wasting the retry budget (exactly 1 call before falling back) — 11/11 tests passing.
- Total failure reporting: verified both at the gateway level and through the actual HTTP endpoint that the caller receives complete, per-candidate failure detail, not a generic error.
- Real-world behavior: the live smoke test against the actual OpenAI and Anthropic endpoints (no keys configured) is the strongest evidence in this exercise — it didn't just confirm the code "works," it surfaced a genuine failure mode the design hadn't specifically anticipated and confirmed the architecture handled it correctly anyway.
- Not evaluated here: a fully authenticated live call to either real provider (no API keys available in this environment, same limitation as the FastAPI/LangChain gateway and tool-calling agent exercises), and streaming responses (not implemented).

## Key Learnings

- Testing against a live, unauthenticated endpoint — even one that's guaranteed to fail — surfaced a real bug class (two providers failing in structurally different ways for the "same" underlying problem, empty credentials) that no amount of MockTransport fixture-writing would have caught, because I would have had to already know to simulate `LocalProtocolError` specifically. Live smoke testing earns its place even when the "happy path" can't be exercised live.
- The retry/fallback boundary is worth naming explicitly as two different questions ("is this worth trying again on the same candidate" vs. "should we give up on this candidate entirely") — collapsing them into one mechanism would have either wasted retry budget on hopeless errors or given up on transient ones too early, and neither mistake is obvious from a quick read of a combined implementation.
- A deliberately broad exception boundary is not automatically bad practice — it depends entirely on what the boundary's job actually is. Here, the job was "isolate one candidate's failure, no matter its shape, so the chain can continue," and the live finding is direct evidence that a narrower, curated list of "expected" exceptions would have missed a real one.
