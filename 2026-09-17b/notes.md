## Implementation

- `Message` is a minimal frozen dataclass (`role`, `content`) — no timestamps, IDs, or metadata, since none of that was needed to demonstrate the core mechanism.
- `RollingConversationMemory.add_message()` appends unconditionally, then checks `len(self.messages) > self._max_messages` — note the strict `>`, not `>=`: at exactly 20 messages, no rollover fires yet (verified by `test_rollover_fires_exactly_once_at_threshold_crossing`), matching "if length **exceeds** 20" from the spec precisely rather than off-by-one.
- `_rollover()` computes `overflow = self.messages[: len(self.messages) - self._keep_recent]` — everything except the most recent `keep_recent` — calls the summarizer with `(self.summary, overflow)`, assigns the result back to `self.summary`, and then trims `self.messages` down to just that same most-recent window. The summarizer call happens *before* the trim, so the overflow messages are still available to read at the moment they're summarized — trimming first would mean summarizing an already-empty slice.
- The constructor validates `keep_recent < max_messages` and raises `ValueError` otherwise — if `keep_recent >= max_messages`, a rollover would either be a no-op (nothing to overflow) or would try to keep more messages than the threshold that triggered it, neither of which is a coherent configuration, so it's rejected at construction time rather than producing confusing behavior later.
- `get_context()` is the one function that matters to an actual caller: it returns `[summary-as-system-message] + recent-messages` if a summary exists, or just the recent messages if no rollover has ever fired yet. This is deliberately a *read-only projection* — calling it doesn't mutate `self.messages` or `self.summary`, so it can be called as often as needed (e.g. once per turn, right before every model call) without side effects.
- `LLMSummarizer` takes an injected `complete: Callable[[str], Awaitable[str]]` rather than owning a provider client directly — the same "depend on an interface, not a concrete provider" pattern as the `LLMClient` protocol in the tool-calling agent exercise and the `ProviderAdapter` protocol in today's LLM gateway exercise. Binding it to a real model call (e.g. `lambda prompt: gateway.complete("openai/gpt-4o-mini", [{"role": "user", "content": prompt}])`) is a one-line integration, not a rewrite.
- `ExtractiveSummarizer` is intentionally *not* trying to be a good summarizer — it's a naive, deterministic fold (prior summary text, if any, followed by one line per overflowed message) whose only job is to make the *mechanism* testable without a real model call: does the prior summary genuinely get carried forward on every rollover, and does information from the overflow genuinely end up somewhere in the result. Both are checkable by simple substring assertions specifically because this summarizer doesn't compress or paraphrase anything away.
- Edge case handled: a conversation that never crosses the threshold has `summary is None` and `get_context()` returns exactly the raw messages with no synthetic system message injected — a short conversation isn't polluted with an empty or placeholder summary.
- Not handled (explicitly out of scope): token-based budgeting (this counts *messages*, not tokens — a real system would likely also cap by token count, since 20 very long messages and 20 one-word messages are very different context-window costs); summarizing the summary itself if it grows unboundedly long over a very long-running conversation (each rollover appends new information, so an extremely long conversation's summary could itself eventually grow large — a production version might periodically re-summarize the summary itself, not attempted here).

## Complexity

- Time: O(1) amortized per `add_message()` call between rollovers; each rollover itself does O(overflow size) work to render messages plus whatever the injected summarizer costs (O(1) locally for `ExtractiveSummarizer`, one network round-trip for `LLMSummarizer`).
- Space: O(max_messages) for raw storage at any instant (bounded, never grows with total conversation length) + O(summary length), which — with `ExtractiveSummarizer` specifically — does grow with conversation length since it never compresses, only appends; a real `LLMSummarizer` backed by an actual model is expected to produce a roughly stable-sized summary instead, which is part of why the extractive version is explicitly labeled a mechanism-proof, not a production summarizer.

## Follow-up Questions

**Why?**
Every model has a finite context window, and any sufficiently long-running conversation or agent session will eventually exceed it if the full raw history is kept and resent on every turn. The two naive alternatives are both bad: truncate old messages (silently loses information, possibly including something the user referenced ten turns ago and expects to still be "remembered") or refuse to continue (breaks the product). Rolling summarization is the standard middle path — bounded size, without silent information loss — used by real conversation-memory implementations (e.g. LangChain's `ConversationSummaryBufferMemory` follows exactly this shape).

**How exactly?**
Every message is appended to a raw list. Once that list exceeds the threshold, everything except a trailing window of recent messages is handed to a summarizer along with whatever summary already existed from a prior rollover; the summarizer's output becomes the new summary, and the raw list is trimmed down to just that trailing window. Assembling context for an actual model call means: the summary (if any) as a leading system message, then the verbatim recent messages.

**Which algorithm?**
Not a named classical algorithm — this is the general shape of "incremental/rolling aggregation over a stream," the same category as a running average or a log-structured merge: each new batch of data is folded into an existing compressed state rather than the whole history being reprocessed from scratch every time. The key correctness property (proven by tests) is that the fold is associative enough that early information reachable through summary A, folded into summary B, is still reachable through summary B — not just through A.

**Which library?**
Standard library only for the mechanism itself (`dataclasses`, `typing.Protocol`) — deliberately no memory/conversation-management library, since the point was implementing and understanding the rolling-fold mechanism directly, the same reasoning as this week's other from-scratch exercises (the tool-calling loop, the LLM gateway).

**What happens internally?**
Nothing exotic — this is plain Python list slicing and one async function call per rollover. The interesting internal property isn't computational, it's the data-flow guarantee: `overflow` is read from `self.messages` *before* the assignment that trims it, and `self.summary` is read as an input to `_summarizer.summarize()` *before* it's overwritten with the result — get either of those two orderings backwards and the "nothing missed" property breaks silently (an empty overflow summarized, or the new summary computed without ever seeing the old one).

**How is it implemented?**
See [Implementation](#implementation) above.

**What if this fails?**
- The injected `complete`/summarizer call fails (a real model call can time out, rate-limit, or error): currently unhandled — `LLMSummarizer.summarize()` would propagate whatever exception the injected callable raises, and `_rollover()` doesn't catch it, meaning a failed summarization currently leaves `self.messages` un-trimmed (the assignment to `self.summary` never happens, so the function raises before reaching the trim line either — actually: `self.summary = await ...` — if the await raises, `self.summary` is never reassigned AND `self.messages` is never trimmed, so the memory object is left exactly as it was before the failed rollover, not corrupted). This "fails atomically, nothing partially updated" behavior is actually correct by accident of Python's execution order rather than by deliberate design — worth calling out as something a more defensive implementation should make an explicit, tested guarantee rather than an emergent property.
- The summarizer returns something nonsensical or empty (a real model hallucinating, or truncating): nothing here validates the summary's content — a production version would likely want a sanity check (non-empty, roughly proportional length) before accepting it as the new summary, not attempted here.
- The conversation never crosses the threshold: `get_context()` degrades gracefully to "just the raw messages," never introducing an empty or placeholder summary.

**What trade-offs did you consider?**
- Counting messages (chosen) vs. counting tokens: message count is simple and was what the problem explicitly specified ("if length exceeds 20 messages"), but 20 messages of one word each and 20 messages of several paragraphs each are very different in actual context-window cost — a production system would likely combine both, or use tokens as the primary budget and messages as a secondary/simpler heuristic.
- `ExtractiveSummarizer` (chosen for testing/demo) vs. requiring a real model call to test at all: the extractive version sacrifices summary *quality* entirely but keeps the *mechanism* fully testable and deterministic — the same trade-off made throughout this week whenever no real API key was available, and named as such rather than presented as if it were a real summarizer.
- Re-summarizing overflow together with the prior summary every rollover (chosen) vs. keeping a list of all past summaries and concatenating them at read time: the chosen approach keeps exactly one summary string at all times (simpler state, bounded growth *if* the underlying summarizer actually compresses, which `ExtractiveSummarizer` deliberately doesn't); keeping a list of summaries would avoid ever re-processing old information but means the "compressed" record keeps growing in count even if each individual summary stays short, and pushes the job of combining them onto whoever reads `get_context()` instead of onto the rollover step.
- No token-budget cap on the summary itself: a very long conversation with `ExtractiveSummarizer` specifically will produce an ever-growing summary (since it never compresses, only appends) — a real `LLMSummarizer` is expected to behave differently (produce a genuinely compressed, roughly stable-sized summary), but this implementation doesn't enforce or verify that as a property, since doing so meaningfully requires an actual model in the loop.

**How do you debug it?**
- `memory.rollovers` (a simple counter) is the first thing to check if a conversation's summary looks wrong or a fact seems missing — zero rollovers means summarization never fired at all (check the threshold/keep_recent configuration), while a rollover count lower than expected for a given message count points at a `keep_recent` set too high relative to `max_messages`.
- To debug whether the *rolling* property specifically (not just "a summary exists") is working, check for a fact known to have been folded in at an *earlier* rollover than the most recent one — `test_summary_accumulates_across_multiple_rollovers_not_just_the_latest_batch` is exactly this check, and is the test that would fail first if someone "simplified" `_rollover()` to only pass the new overflow to the summarizer and dropped the prior-summary argument.
- For `LLMSummarizer` specifically, capturing the actual prompt sent to the injected `complete` callable (as the tests do) is the way to confirm the prior summary and the new messages are both genuinely present in what the model receives, rather than assuming the string-building logic is correct from reading it.

**How do you evaluate it?**
- Boundedness: raw message count never exceeds `max_messages` even after 200 additions (verified directly).
- Threshold precision: no rollover at exactly the threshold, exactly one rollover immediately after crossing it (verified — this is the "exceeds," not "reaches," distinction from the spec).
- The core "nothing missed" property: a fact from the very first messages (long trimmed from raw storage) and a fact folded in at a *different, later* rollover are both independently verified present in the final summary — this is the test that actually matters for this problem, more than the mechanical bookkeeping around it.
- Context assembly: verified that `get_context()` places the summary first (when one exists), preserves the raw messages' order and content exactly, and introduces no summary message at all before the first rollover.
- The injected-model-call seam: verified that `LLMSummarizer` builds a prompt containing both the prior summary and the new messages' content, and correctly handles the "no prior summary yet" case with an explicit placeholder rather than e.g. the string `"None"` leaking into the prompt.
- Not evaluated here: a real model's actual summarization quality (no API key available, same limitation as this week's other genai-agentic exercises), and behavior under a failed summarization call (identified above as an emergent rather than deliberately-tested guarantee).

## Key Learnings

- "Rolling" is doing real work in the name — the entire correctness property of this exercise hinges on the summarizer receiving the *previous* summary as an input on every rollover, not just the newest overflow. It would be easy to write a version that looks correct (compiles, has a summary, passes a shallow test) while quietly losing everything before the second rollover, and the only way to actually catch that is a test that specifically checks for information from *two different* rollover windows.
- Separating "prove the mechanism" from "prove summary quality" (via the deliberately non-compressing `ExtractiveSummarizer`) made it possible to fully and deterministically test the part of this exercise that's actually about engineering correctness, without needing a real model call to validate the part that's genuinely about model quality — a distinction worth drawing explicitly whenever a component's correctness and its output quality are separable concerns.
- The "fails atomically by accident of statement ordering, not by design" finding (in **What if this fails?**) is itself a useful habit to bring to future code review: an accidentally-correct failure-safety property is a liability until it's made an explicit, tested guarantee — otherwise a later refactor can break it without anything visibly wrong at the time.
