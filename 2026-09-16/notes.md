## Implementation

- `ToolCall`/`AssistantMessage` are frozen dataclasses shaped exactly like OpenAI's tool-calling response: an assistant turn either carries `content` (a final answer) or a list of `tool_calls`, never a bespoke in-between representation invented for this exercise.
- `Tool` bundles a name, description, JSON-schema parameters, and the actual Python callable, with `.schema()` producing the exact `{"type": "function", "function": {...}}` shape the `tools=` parameter expects — the schema and the implementation live on one object so they can't drift apart.
- `run_agent()`'s loop body does exactly three things per iteration: call the LLM, append its message to the transcript, and — if it requested tools — execute each one and append its result. The `for _ in range(max_iterations)` structure means falling off the end of the loop (no `return` ever hit) is the *only* way to reach the `raise AgentGaveUpError(...)` after it — termination is structural, not something a forgotten counter increment could silently break.
- `_execute_tool_call` is deliberately the single choke point for every tool-related failure: it looks up the tool (unknown → error), parses the JSON arguments (malformed → error), and calls the tool (exception → error) — each failure short-circuits to a `json.dumps({"error": ...})` string, and the function's return type is always `str`, never an exception. This mirrors the same "push failure handling into the unit, not around it" pattern from [[async-retry-backoff]] and [[async-multi-api-fetch]].
- `calculate()` parses the expression with `ast.parse(..., mode="eval")` and walks the resulting tree in `_safe_eval`, which only recurses into `ast.Constant` (numbers only), `ast.BinOp`/`ast.UnaryOp` with operators from a small whitelist (`+ - * / ** unary-`), and raises `ValueError` on anything else — a function call, an attribute access, a comprehension, a conditional expression. This is why `__import__(...)`, `[].{}.__class__...`, and even a plain ternary all correctly fail: none of those node types are in the whitelist, so there's no path through `_safe_eval` that reaches them.
- `get_weather()` does two real HTTP calls (geocode the city name to lat/lon, then fetch current weather for those coordinates) against open-meteo's free, keyless API — chosen specifically so at least one tool in the demo produces genuinely unpredictable output that the "model" (a scripted policy) has to actually react to, not just echo back.
- `ScriptedLLMClient` wraps a `policy(messages) -> AssistantMessage` callable rather than a fixed list of canned responses — the policies (`_weather_then_calc_policy`, etc.) inspect the transcript for prior tool results and branch on their *actual content* (e.g. reading the real temperature out of `get_weather`'s result to build the next `calculate` call), which is what makes the multi-step demo a genuine test of the loop's data flow rather than a fixed script playing out regardless of what happens.
- `OpenAIChatClient` translates a real `chat.completions.create()` response into the same `AssistantMessage`/`ToolCall` shape `ScriptedLLMClient` produces — written to prove the interface is real and swappable, not exercised live (no API key in this environment).
- Edge case handled: a single assistant turn can request *multiple* tool calls at once (real tool-calling APIs support this) — the loop's inner `for tool_call in assistant.tool_calls` already handles that without special-casing the single-call case.
- Not handled (explicitly out of scope): parallel tool execution when multiple tools are requested in one turn (they're executed sequentially here); conversation memory/state across separate `run_agent()` invocations (each call starts a fresh transcript); and streaming partial responses (this loop assumes a complete `AssistantMessage` per turn, not token-by-token).

## Complexity

- Time: O(max_iterations) LLM calls in the worst case, each followed by O(tool_calls_in_that_turn) tool executions; each real tool call's own cost (e.g. `get_weather`'s two HTTP round trips) is separate from the loop's own overhead, which is O(1) per iteration.
- Space: O(iterations × messages_per_iteration) for the transcript, since every turn and every tool result is appended and never pruned — a long-running agent would eventually need to summarize or truncate history, not attempted here (out of scope for a bounded `max_iterations`).

## Follow-up Questions

**Why?**
Every agent framework — LangChain's agents, LangGraph, OpenAI's Assistants API, a hand-rolled ReAct loop — reduces to this same shape: give the model a menu of actions, let it request one, execute it, show it the result, repeat. Understanding this loop directly (rather than only ever calling `AgentExecutor.run()`) is what makes debugging a misbehaving agent, or explaining in an interview *why* an agent looped forever or hallucinated a tool, actually possible instead of being a black box.

**How exactly?**
`run_agent()` seeds a message list with a system prompt and the user's message, then loops: ask the LLM client for its next move given the current transcript and available tool schemas; if it answered directly, that's the final result; if it requested one or more tools, execute each (never letting a failure escape), append every result as a `role: "tool"` message tagged with the originating `tool_call_id`, and loop back so the model sees those results on its next turn.

**Which algorithm?**
This is the ReAct pattern (Reason + Act, interleaving the model's reasoning turns with tool-execution turns) reduced to its essential control flow — not a novel algorithm, but a specific, well-known agent architecture implemented directly rather than through a framework's abstraction of it.

**Which library?**
Standard library only for the loop and the safe-arithmetic tool (`ast`, `json`, `operator`) — no agent framework. `httpx` for the one real network tool. `openai` only inside `OpenAIChatClient`, imported lazily (inside `__init__`, not at module top level) so importing `solution.py` and running the fully-offline demo/tests never requires the `openai` package to even be installed correctly configured.

**What happens internally?**
Each iteration is one blocking (here; could be `async` the same way as [[async-multi-api-fetch]]) call to the model, which — for a real provider — runs the full chat completion inference and, if the model's next-token distribution favors it, emits a structured tool-call object instead of freeform text (this is a capability the underlying model is specifically trained/fine-tuned for, not something bolted on by the API). The loop itself does no inference; it's pure orchestration around whatever the model decides.

**How is it implemented?**
See [Implementation](#implementation) above.

**What if this fails?**
- The model requests a tool that doesn't exist (hallucination, or a stale tool schema list): caught in `_execute_tool_call`, fed back as `{"error": "unknown tool ..."}`, model gets a chance to recover on its next turn. Verified: scenario 3 shows exactly this recovery.
- The model's tool-call arguments aren't valid JSON: caught, fed back, same recovery path. Verified: scenario 4.
- The tool itself raises (a real exception from real code, e.g. `get_weather` on a nonexistent city): caught, fed back as the exception's type and message, same recovery path. Verified: scenario 5, using a genuine failure from the real API rather than a synthetic one.
- The model never stops requesting tools (a bug in the model, an adversarial prompt, or a policy that's simply wrong): `AgentGaveUpError` fires at `max_iterations`, bounding both the wall-clock time and the API cost of a single `run_agent()` call. This is the single most important safety property of the whole exercise — without it, a bad model output or a bad tool becomes an unbounded loop spending real API budget forever.
- The real `get_weather` API itself is unreachable/slow: currently propagates as whatever `httpx` exception surfaces, caught generically by `_execute_tool_call`'s broad `except Exception` and turned into a fed-back error — the model would see a generic connection-error message rather than a specifically-classified one. A production version would likely reuse [[async-retry-backoff]]'s classifier here to distinguish "retry this" from "give up," not attempted today to keep scope to the agent loop itself.

**What trade-offs did you consider?**
- `ScriptedLLMClient` driven by a policy function (chosen) vs. a fixed list of canned responses: a fixed list can't react to `get_weather`'s genuinely unpredictable real output, so it would either have to fake the tool result too (weakening the "real integration" claim) or hardcode an expected temperature (making the test brittle against real weather changing). A policy function keeps the tool call real while keeping the "model" fully deterministic and offline.
- Sequential tool execution within one turn (chosen) vs. concurrent execution (à la [[async-multi-api-fetch]]) when a model requests multiple tools at once: sequential is simpler and was sufficient for every scenario this exercise needed; a high-throughput agent serving many independent tool calls per turn would reasonably reach for `asyncio.gather` here, the same pattern already proven out on a different day.
- A hard `max_iterations` cutoff (chosen) vs. a cost/token budget cutoff: iteration count is simple and was sufficient to demonstrate the safety property, but a production agent typically cares more directly about total tokens or dollars spent than raw turn count — a real deployment would likely track both.
- No conversation memory across separate `run_agent()` calls: each call is stateless and self-contained, which keeps the loop simple and easy to reason about, at the cost of not supporting a genuinely multi-turn conversation (a real chat agent would need to persist and re-supply prior turns' transcripts) — left out to keep today's scope to the tool-calling mechanism itself.

**How do you debug it?**
- The `transcript` returned alongside the final answer (not just the answer itself) is the primary debugging surface — every model turn and every tool result, in order, with `tool_call_id` linking each result back to the call that produced it. This is exactly what you'd log in a real deployment to reconstruct "why did the agent do that."
- To debug a specific tool failure, `_execute_tool_call`'s error strings are structured (`{"error": "<type>: <message>"}` or `{"error": "unknown tool ..."}"}`) rather than free text, so they're greppable/parseable from logs, not just human-readable in isolation.
- To confirm the safety property of `calculate()` isn't accidentally weakened by a future change, the parametrized `test_calculate_rejects_anything_beyond_arithmetic` test is itself the debugging tool — a regression here (a previously-rejected expression suddenly succeeding) would fail loudly and specifically, not silently.
- To reproduce the "model never stops" failure mode deterministically for testing, `_never_finishes_policy` always requests another (harmless) tool call — no need to wait for a real model to actually misbehave to verify the guard works.

**How do you evaluate it?**
- Orchestration correctness (offline, deterministic, in `test_solution.py`): no-tool-needed path, a single tool round-trip, error recovery for a raising tool, and the `max_iterations` guard — 18/18 tests passing, run in 0.01s since nothing here touches the network.
- Real integration: the demo's scenario 2 makes two genuine HTTP calls (geocoding + weather) and correctly threads the real returned temperature through a second tool call (`calculate`) into a final answer — re-run twice against the live API with consistent success (different real temperatures, same correct arithmetic).
- Safety: `calculate()` correctly evaluates six arithmetic cases and correctly rejects four different code-execution attempts smuggled in as "expressions," including a `__import__` call, a file read, a class-hierarchy walk (a classic Python sandbox-escape technique), and even an otherwise-harmless ternary expression (rejected because it's simply not in the arithmetic whitelist, which is the correct, conservative default — allow only what's explicitly needed, not "allow everything except known-bad things").
- Not evaluated here: `OpenAIChatClient` against a real OpenAI account (no API key available), and behavior under truly concurrent/parallel tool-call execution within a single turn (not implemented, see trade-offs).

## Key Learnings

- The entire safety story of a tool-calling agent rests on one design choice: does a bad tool call raise, or does it become data fed back to the model? Choosing "becomes data" at the `_execute_tool_call` boundary is what makes hallucinated tool names and malformed arguments *recoverable* failure modes instead of crashes — the same principle as `fetch_source` in the async multi-API exercise, applied to a new kind of failure.
- A scripted stand-in "LLM" that reacts to real tool output (via a policy function reading the transcript) is a meaningfully better test double than one that returns a fixed sequence of responses — it actually exercises the data flow between tool results and subsequent decisions, which is the part of an agent loop most likely to have a real bug.
- `ast`-based expression evaluation is the concrete, checkable version of "never `eval()` untrusted input" — a whitelist of allowed node types is something you can point to and test exhaustively (this exercise's four rejected-expression tests), whereas a blacklist approach ("block anything that looks like an import") is exactly the kind of incomplete defense that real sandbox escapes route around.
